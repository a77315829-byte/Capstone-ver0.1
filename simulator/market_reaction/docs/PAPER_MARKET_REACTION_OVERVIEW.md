# 과거시장시뮬(Market Reaction Simulator) 시스템 개요

> 논문 작성용 자료. `simulator/market_reaction` 전체 시스템(RAG 서브시스템 포함)을 설명한다.
> 출처: `README.md`, `docs/market_reaction_backend_spec.md`, 실제 구현 코드(`app/`).

## 1. 개요 및 목적

과거시장시뮬(Market Reaction Simulator)은 모의투자 사용자가 임의의 뉴스·이벤트·시나리오
텍스트를 입력하면, 해당 정보가 특정 종목의 시장에 어떤 영향을 미칠지를 **투자자 유형별
관점에서 분석**해 교육적으로 설명해 주는 시스템이다. 실시간 시세 데이터를 다루는
"실시간 모의투자" 시뮬레이터와 구분되는, **과거 공시·뉴스 기반의 시장 반응 학습**
목적의 서비스다.

핵심 설계 원칙은 다음과 같다.

- **직접적인 매수·매도 추천이나 구체적 가격 예측을 하지 않는다.** 시장이 어떤 방향으로,
  어떤 강도로 반응할 가능성이 있는지를 설명하는 데 그친다(교육용 목적의 명시적 제약).
- **LLM 장애에 대해 항상 정상 응답한다.** 로컬 LLM(Ollama)이 완전히 꺼져 있어도
  rule-based fallback으로 대체해 서비스가 절대 실패하지 않는다.
- **stateless API**다. 이 서비스 자체는 결과를 저장하지 않으며, 저장/조회는 별도의
  Node.js 백엔드 + MongoDB 계층이 담당한다.

기술 스택: Python **FastAPI**(비동기 REST API), 로컬 LLM **Ollama**(Llama 3.1 8B),
**FAISS**(벡터 유사도 검색), **MongoDB Atlas**(RAG 데이터 저장), 로컬 임베딩 모델
**bge-m3**(다국어, 한국어 검색 성능 우수). Node.js/Express 백엔드가 프론트엔드
요청을 그대로 프록시하는 구조로 붙어 있다.

## 2. 전체 처리 파이프라인

사용자가 종목과 입력 텍스트를 제출하면(`POST /simulate`), 다음 단계를 순차·병렬로
거쳐 최종 분석 결과를 생성한다.

```
사용자 입력 (종목 + 텍스트)
  ① 입력값 적합성 검증 (validator)         — 형식은 rule-based, 의미 판단은 LLM
  ② 외부 시장 맥락 분석 (external_context)  — RAG로 검색한 공시 문서를 근거로 LLM 분석
  ③ 실시간 모의투자 맥락 분석 (realtime_context) — 현재가/등락률 등 rule-based 분석
  ④ 표준 입력 통합 (integrator)             — ②③ 결과를 표준 스키마로 통합
  ⑤ 5개 투자자 유형 에이전트 병렬 분석 (agents) — 각자의 관점에서 반응 생성
  ⑥ 에이전트 결과 정합성 검토 (critic)
  ⑦ 시장 압력 산출 (pressure)   — 순수 함수
  ⑧ 시장 분위기 산출 (sentiment) — 순수 함수
  ⑨ 분석 신뢰도 산출 (confidence) — 순수 함수
  ⑩ 종합 해설 생성 (summary)     — LLM
  → 최종 JSON 응답
```

①·②·⑤·⑥·⑩ 5단계 + 에이전트 5개를 합쳐 총 **9개의 LLM 호출 지점**이 있으며, 각각
독립적으로 실패해도 해당 모듈만 rule-based 대체 로직으로 전환된다(3절 참고).

## 3. 안정성 설계 — 모듈 단위 Fallback

이 시스템의 핵심 설계는 "LLM이 실패해도 서비스는 절대 실패하지 않는다"이다.

- 9개 LLM 호출 지점 각각이 독립적으로 실패를 흡수한다. 예를 들어 5개 에이전트 중
  2개만 LLM 호출이 실패하면, 그 2개만 rule-based 대체 로직으로 채워지고 나머지
  3개는 LLM 결과를 그대로 사용한다.
- Ollama가 완전히 꺼져 있어도 9개 모듈 전부 fallback으로 채워 **HTTP 200**을 반환한다
  (500 에러를 내지 않는다).
- 입력값 부적합 판정(직접 매수/매도 추천 요청 등)은 fallback과 별개로, 검증 단계에서
  **HTTP 422**로 즉시 거절한다.
- 응답의 `meta.llm_status` 필드로 이 상태를 노출한다: `ok`(fallback 0개) /
  `partial_failure`(1~8개) / `fallback`(9개 전부).
- fallback이 발생하면 `analysis_confidence` 점수에서 모듈당 -0.05씩 감점되어,
  사용자가 결과의 신뢰도를 판단할 수 있도록 한다.

## 4. 5개 투자자 유형 에이전트 모델

시장 참여자를 5개 유형으로 나누어, 동일한 정보에 대해 서로 다른 관점의 반응을
시뮬레이션한다.

| 에이전트 | 관점 | 판단 기준 |
|---|---|---|
| 개인 투자자 | 화제성 / 투자심리 | 테마성, 뉴스 주목도, 대중 관심, 단기 기대감 |
| 기관 투자자 | 실적 / 가치평가 | 실적 개선, 밸류에이션, 리스크, 포트폴리오 |
| 외국인 투자자 | 글로벌 투자흐름 | 환율, 금리, 글로벌 산업흐름, 외국인 수급 |
| 단기 투자자 | 모멘텀 / 변동성 | 뉴스 반응속도, 거래량, 단기 흐름, 변동성 |
| 장기 투자자 | 장기 성장성 | 산업 지속성, 경쟁력, 재무 안정성, 장기 실적 |

각 에이전트는 표준화된 입력(StandardInput)을 받아 자신의 관점에서
`{반응 방향(매수/매도/관망), 반응 강도(낮음/중간/높음), 근거, 리스크 요인}`을
생성한다. 사용자의 실제 보유 수량·평균 매입가·손익 상태는 **의도적으로 어떤 단계에도
반영하지 않는다** — 이 시스템은 사용자 개인의 포지션이 아니라 시장 전체의 반응을
설명하는 것이 목적이기 때문이다.

## 5. 시장 압력 산출 알고리즘

5개 에이전트의 반응을 정량적으로 종합해 매수/매도/관망 압력을 백분율로 산출한다.
순수 함수(LLM 미사용)로 구현되어 결정론적이고 테스트 가능하다.

**1) 에이전트별 반응 점수**
```
agent_score = strength_score × base_weight × input_relevance
```
- `strength_score`: 반응 강도(낮음=1, 중간=2, 높음=3)
- `base_weight`: 사건 유형(event_type)별로 미리 정의된 투자자군 가중치(코드 상수 표,
  LLM이 아닌 결정론적 로직으로 조회). 예: 실적 발표(`earnings`)는 기관 투자자 가중치가
  0.30으로 높고, 금리·환율 변동은 외국인 투자자 가중치가 0.35까지 올라간다. 어느 표를
  쓰든 5개 값의 합은 항상 1.00이다.
- `input_relevance`: 해당 에이전트의 판단 기준과 입력 정보의 관련도(낮음=0.8 /
  보통=1.0 / 높음=1.2)

**2) 압력 백분율 산출**
```
total = Σ 전체 에이전트의 agent_score
buy_pressure  = Σ(매수 에이전트 점수) / total × 100
sell_pressure = Σ(매도 에이전트 점수) / total × 100
hold_pressure = Σ(관망 에이전트 점수) / total × 100
```
정수 %로 반올림하되 세 값의 합이 100이 되도록 잔여값을 보정한다.

## 6. 시장 분위기 및 분석 신뢰도

**시장 분위기(sentiment)**는 위에서 산출한 매수/매도/관망 압력을 규칙 기반으로
6단계(매우 긍정적/긍정적/중립적/부정적/매우 부정적/불확실성 확대)로 분류하는 순수
함수다. 예: 매수 압력이 75% 이상이고 매도 압력이 10% 이하이면 "매우 긍정적", 관망
압력이 최댓값이고 40% 이상이면 "불확실성 확대"로 분류한다.

**분석 신뢰도(analysis_confidence)**는 이 분석 결과를 얼마나 신뢰할 수 있는지를
0~1 점수로 정량화한 지표로, 아래와 같이 5가지 요소의 가중합으로 계산한다.

```
analysis_confidence =
  입력 구체성        × 0.20   (입력 텍스트 길이 기반)
+ 종목 관련성        × 0.20   (종목명/산업 키워드 직접 포함 여부)
+ 데이터 완전성      × 0.20   (실시간 시세 vs stub 시세 사용 여부)
+ 분석 일관성        × 0.25   (에이전트 간 결과 충돌 정도)
+ 불확실성 점수      × 0.15   (도출된 불확실성 요인 개수)
```
여기에 LLM fallback 모듈 1개당 -0.05, stub 시세 사용 시 -0.10의 추가 감점이 적용되며,
최종 점수는 0.75 이상 "높음", 0.5 이상 "보통", 그 미만 "낮음"의 3단계 등급으로 표시된다.
이 점수는 사용자에게 "이 분석 결과를 얼마나 신뢰하고 참고해야 하는지"에 대한 참고
지표로 제공되며, 실제 시장 예측의 정확도를 보장하지 않는다는 점을 응답에 명시한다.

## 7. RAG(검색 증강 생성) 서브시스템

②단계(외부 시장 맥락 분석)의 근거 자료를 확보하기 위해, 종목별 실제 공시 문서를
검색해 LLM 프롬프트에 참고 자료로 주입하는 RAG 파이프라인을 갖추고 있다.

**데이터 원천**: 한국 20개 종목은 DART(전자공시시스템) Open API, 미국 20개 종목은
SEC EDGAR에서 사업보고서·정기공시 문서를 수집한다.

**색인 구축(오프라인 배치)**: 수집한 문서를 구조적 경계(보고서 항목, EDGAR Item
단위) 기준으로 청킹하고, 로컬 임베딩 모델(bge-m3, 1024차원)로 벡터화한다. 표가
텍스트로 펼쳐지며 반복되는 각주, 지나치게 짧은 조각 등 검색 품질을 저해하는 청크는
휴리스틱 필터로 걸러낸다.

**저장 및 검색(런타임)**: 청크 텍스트와 임베딩 벡터는 **MongoDB**에 영속 저장하고,
런타임에는 종목이 처음 검색될 때만 해당 데이터를 메모리로 읽어 **FAISS** 인덱스를
만들어 코사인 유사도 검색에 사용한다. 즉 MongoDB는 데이터 원본(source of truth),
FAISS는 순수 검색 캐시 역할로 계층을 분리했다 — 이렇게 하면 검색 자체는 항상 로컬
메모리 연산이라 요청 지연에 영향이 없으면서도, 서버 재배포 시 데이터가 유실되지 않고
여러 서버 인스턴스가 동일한 색인을 공유할 수 있다. 인덱스 재구축은 종목 단위로
버전을 증가시키며 중간 실패에도 데이터 정합성이 깨지지 않는 절차(restart-safe
versioned rebuild)로 설계했다. 총 40개 종목, 약 39,000개 청크가 색인되어 있으며,
임베딩을 32비트 부동소수점 압축 포맷으로 저장해 검색 정확도 손실 없이 저장 용량을
약 58% 절감했다(FAISS가 검색 시점에 어차피 32비트 정밀도로 계산하기 때문에 저장
포맷만 이에 맞춘 것으로, 정밀도 손실은 없다).

검색은 종목이 지원 대상이 아니거나, 데이터가 없거나, 임베딩 모델 불일치, 연결 실패
등 어떤 이유로도 실패할 경우 예외를 던지지 않고 빈 결과를 반환해, 3절의 fallback
설계 원칙과 일관되게 서비스 안정성을 해치지 않는다.

## 8. 실시간 시세 연동

실시간 모의투자 계좌 정보를 다루는 별도 서비스(KIS 증권 API 연동)로부터 현재가·
등락률 등을 전달받으면 이를 반영하고(`data_source: external_api`), 전달이 없거나
실패하면 미리 정의된 stub 데이터로 자동 대체한다(`data_source: stub`). 이 여부는
분석 신뢰도 점수와 응답 메타데이터에 그대로 노출된다.

## 9. 검증

- 시장 압력·분위기·신뢰도 산출은 순수 함수로 구현해 단위 테스트로 수식·경계값을
  검증했다(예: 대표 에이전트 조합에 대해 매수 69% / 매도 0% / 관망 31%가 정확히
  산출되는지).
- Ollama를 강제로 끈 상태에서 9개 모듈 전부가 fallback으로 채워지고도 정상 응답이
  생성되는지를 오프라인 E2E 테스트로 검증했다.
- RAG 서브시스템은 실제 DART/EDGAR API로 문서를 수집·색인해 실 데이터 기준으로
  검색이 정상 동작함을 확인했다.
- 전체 테스트 스위트(247개)가 CI 환경에서 Ollama·외부 네트워크 없이도 통과하도록
  구성했다(오프라인 fallback 경로 기준).

## 10. 한계 및 향후 과제

- 5개 투자자 유형의 event_type별 가중치 표는 실증 데이터로 보정된 값이 아니라
  설계 단계의 휴리스틱이다.
- RAG는 현재 한국 20종목·미국 20종목으로 지원 범위가 제한되어 있으며, 대상 확대
  시 저장 용량(현재 MongoDB Atlas 무료 티어 512MB 중 약 50% 사용)을 함께 고려해야
  한다.
- 공시 문서 자동 재수집(주기적 갱신)은 아직 구현하지 않았고, 현재는 수동 배치
  실행 방식이다.
