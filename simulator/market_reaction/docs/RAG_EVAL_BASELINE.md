# 정답 기반 평가 — 베이스라인, 개선 시도, 상한선, 데이터 개선

> 앞선 `RAG_ABLATION_RESULT.md` 는 "RAG 를 켜고 끄면 결과가 **바뀌는가**" 를 측정했다.
> 이 문서는 정답 라벨을 만들어 "**맞는가**" 를 측정한 결과다.
>
> 재현:
> ```
> python -m scripts.build_eval_set     # 정답 세트 생성 (DART + KIS)
> python -m scripts.eval_rag           # RAG on/off 정확도 측정
> ```

## 1. 정답 세트

| 항목 | 값 |
|---|---|
| 이벤트 | DART **주요사항보고서**(`pblntf_ty="B"`), 2025-01-01 ~ 2026-09-30 |
| 종목 | RAG 인덱스의 한국 20종목 중 공시가 있는 17종목 |
| 케이스 | **159건** |
| 정답 라벨 | 공시 직전 거래일 종가 → 직후 거래일 종가의 **KOSPI 대비 초과수익률** |
| 밴드 | ±0.5%p 밖일 때만 positive/negative, 안이면 neutral |
| 라벨 분포 | negative 74 (47%) / positive 58 (36%) / neutral 27 (17%) |
| 건전성 | 초과수익률 평균 **+0.00%p** — 체계적 편향 없음 |

**이벤트로 주요사항보고서를 쓴 이유**: 법령이 "주요사항"으로 규정한 공시라 분석자가
자의적으로 고른 것이 아니고, 접수일과 종목이 확정되어 있다. 또 RAG 인덱스는
정기공시(`pblntf_ty="A"`)로 구성되어 있어 **이벤트 문서 자체가 검색되는 누출이 없다.**

**미래 정보 누출 차단**: 검색 기준일을 공시 접수일로 고정해 그 이전 공시만 근거로 쓴다
(`retrieve_relevant_documents(..., published_before=...)`).

### 1.1 수집 과정에서 잡은 라벨 오염 버그

KIS 지수 API 는 호출당 **50행**까지만 반환한다(종목 API 는 100행). 같은 크기의 날짜
윈도우로 호출하면 지수 시계열에만 구멍이 생겨 318/421 거래일만 수집된다.

이 상태에서 종목·지수의 **교집합**으로 기준일을 고르면, 하루 수익률 대신 며칠치 수익률을
조용히 계산해 라벨이 오염된다. 실제로 버그가 있던 최초 수집(155건)과 수정 후(159건)의
라벨 분포가 달랐다(negative 76→74, positive 53→58).

대응: 거래일 달력은 **종목 시세 기준**으로 잡고, 지수에 두 날짜가 모두 있을 때만 라벨을
만든다(없으면 해당 케이스를 버린다). 회귀 테스트로 고정했다.

## 2. 결과 (llama3.1:8b, temperature 0, fallback 0/318건)

| 지표 | RAG ON | RAG OFF | 다수클래스 기준선 |
|---|---|---|---|
| 전체 정확도 | **22.6%** (36/159) | **17.6%** (28/159) | **46.5%** |
| 방향 케이스 정확도 | 9.1% (12/132) | 2.3% (3/132) | — |
| 반대 방향 예측 | 6/132 | 4/132 | — |

> **두 조건 모두 다수클래스 기준선(46.5%)에 크게 못 미친다.**
> 즉 현재 ②단계는 "무조건 negative 로 찍기" 보다 나쁘다.

### 2.1 원인 — 예측 분포가 정답 분포와 어긋나 있다

| | positive | neutral | negative |
|---|---|---|---|
| **정답** | 36% | 17% | **47%** |
| 예측 (RAG ON) | 13% | **87%** | **1%** |
| 예측 (RAG OFF) | 5% | **94%** | **1%** |

`negative` 예측이 **159건 중 1건**이다. 정답의 47% 가 negative 인데도 모델은 거의 전부
`neutral` 로 회피한다.

**이것은 라벨 품질과 무관한 병리다.** 정답이 완벽하더라도, 정답 neutral 이 17% 인 문제에서
87% 를 neutral 로 답하는 예측기는 잘못 동작하는 것이다.

### 2.2 혼동행렬 (행=정답, 열=예측)

```
[RAG ON]                              [RAG OFF]
           pos  neu  neg                         pos  neu  neg
  positive  12   46    0                positive   3   55    0
  neutral    2   24    1                neutral    1   25    1
  negative   6   68    0                negative   4   70    0
```

정답이 negative 인 74건 중 모델이 negative 로 맞힌 것은 **0건**이다.

### 2.3 RAG 효과 — 개선되지만 통계적으로 유의하지 않다

짝지은 비교(McNemar 정확검정, 중복 날짜 제외 n=139):

| | 건수 |
|---|---|
| RAG on 만 맞음 | 6 |
| RAG off 만 맞음 | 2 |
| 둘 다 맞음 | 21 |
| 둘 다 틀림 | 110 |

**p = 0.29 — 유의하지 않다.** 방향 정확도가 2.3% → 9.1% 로 4배가 되긴 했으나 절대 건수가
3건 → 12건이라 표본이 너무 작다. **"RAG 가 정확도를 올린다" 고 주장할 수 없다.**

다만 모델이 방향을 확신했을 때의 정밀도는 차이가 있다:

| | positive 예측 건수 | 그중 정답 | 정밀도 |
|---|---|---|---|
| RAG OFF | 8 | 3 | 37.5% |
| RAG ON | 20 | 12 | **60.0%** |

RAG 가 켜지면 모델이 방향을 더 자주 확신하고(8건 → 20건), 확신했을 때 더 자주 맞는다.

## 3. 결론

1. **현재 ②단계는 다수클래스 기준선보다 나쁘다**(22.6% vs 46.5%). 사용 가능한 수준이 아니다.
2. 원인은 검색 품질이 아니라 **판정 분포의 붕괴**다 — `neutral` 87%, `negative` 1%.
   `RAG_ABLATION_RESULT.md` §5 에서 "병목은 ②단계 프롬프트" 라고 한 결론이 정답 기반
   측정으로 확정됐다.
3. RAG 는 모든 지표에서 개선을 보이지만 **통계적으로 유의하지 않다**(p=0.29).
   RAG 의 근거는 여전히 "정확도 향상" 이 아니라 "근거의 사실성"(`RAG_ABLATION_RESULT.md` §2)이다.

## 4. 한계

- **라벨 노이즈**: 다음 거래일 초과수익률은 단일 공시만으로 결정되지 않는다. 정답 자체가
  시끄럽다.
- **공시 시각 미반영**: DART `list.json` 은 접수일만 주고 시각을 주지 않는다. 장중 공시는
  당일에 이미 반영됐을 수 있다.
- **이벤트 편중**: 159건 중 73건(46%)이 자기주식 취득/처분이다.
- **입력 텍스트가 짧다**: 공시 제목만 쓴다(예: `"삼성전자 공시: 주요사항보고서(자기주식취득결정)"`).
  뉴스 본문이 아니라 ②단계가 쓸 재료가 적다. 뉴스 API 자격증명이 확보되면 개선 가능하다.
- 위 한계들은 정확도의 절대 수준을 깎을 수 있으나, **2.1 의 예측 분포 붕괴는 설명하지
  못한다** — 그것은 입력이나 라벨이 아니라 프롬프트·모델 쪽 문제다.

# 5. 개선 시도 1 — 프롬프트 수정 (실패)

2절의 진단("모델이 neutral 로 회피한다")에 직접 대응하도록 ②단계 시스템 프롬프트를
고쳤다. 관찰된 실패 모드에 1:1 로 대응시킨 수정이다.

| 관찰된 실패 | 프롬프트 수정 |
|---|---|
| 업종 일반론 | `"market analyst"` → `"equity analyst"`, **"ONE SPECIFIC COMPANY"**, "같은 업종 두 기업이 반대로 영향받을 수 있다" 명시 |
| 검색 문서 미활용 | `"background context"` → **"use these as the evidence base"** |
| 뉴스 재진술 | "뉴스가 이미 말한 것을 factor 로 쓰지 말 것" |
| `neutral` 회피 | **"neutral 은 구체적 호재·악재가 실제로 상쇄될 때만. 판단 회피용으로 쓰지 말 것"** |
| 위험을 호재로 분류 | "위험이나 비용 증가는 절대 positive factor 가 아니다" |

**결과: 의도와 정반대로 악화됐다.**

| 버전 | RAG ON | RAG OFF | neutral 예측 |
|---|---|---|---|
| 베이스라인 | 22.6% | 17.6% | 138 / 150 |
| **프롬프트 v2** | **19.5%** | **19.5%** | **155 / 154 (97%)** |

`neutral` 을 명시적으로 금지했는데 오히려 138 → 155 로 늘었고, `positive` 예측은
20 → 2 로 붕괴했다. **RAG on/off 차이까지 사라졌다**(19.5% vs 19.5%).

**해석**: factor 생성 조건을 까다롭게 만들수록("뉴스 재진술 금지", "사업 구조에 근거",
"위험은 호재가 아님") 모델이 factor 를 적게 만들고, factor 가 적으면 방향이 `neutral` 로
떨어진다. **제약 강화가 회피를 늘리는 구조**다. 프롬프트 문구의 문제가 아니다.

# 6. 개선 시도 2 — 구조 변경 (부분 성공, 정확도는 개선 없음)

프롬프트를 베이스라인으로 되돌리고(변수를 하나로 유지) 구조를 바꿨다.

**`impact_direction` 을 LLM 의 선택지에서 제거하고 factor 구성에서 유도한다.**

```python
def derive_impact_direction(positive_factors, negative_factors):
    if len(positive_factors) > len(negative_factors):  return POSITIVE
    if len(negative_factors) > len(positive_factors):  return NEGATIVE
    return NEUTRAL
```

출력 스키마에서 `impact_direction` 을 빼 LLM 이 더 이상 방향을 고르지 않게 하고,
파싱 직후 유도값을 주입한다. 하류(`agents`/`critic`/`summary`/`realtime_context`)는
`external_context` 에서 읽으므로 변경이 없다.

## 6.1 결과

| 버전 | 조건 | 정확도 | 방향정확도 | positive | neutral | negative |
|---|---|---|---|---|---|---|
| 베이스라인 | rag_on | **22.6%** | 9.1% | 20 | 138 | 1 |
| 베이스라인 | rag_off | 17.6% | 2.3% | 8 | 150 | 1 |
| 프롬프트 v2 | rag_on | 19.5% | 3.0% | 2 | 155 | 2 |
| 프롬프트 v2 | rag_off | 19.5% | 3.0% | 2 | 154 | 3 |
| **구조 v3** | rag_on | 19.5% | 8.3% | **41** | **117** | **1** |
| **구조 v3** | rag_off | 20.1% | 5.3% | 14 | 144 | 1 |

회피는 실제로 줄었다 — `neutral` 138 → 117, `positive` 20 → 41. **그러나 정확도는
개선되지 않았다**(22.6% → 19.5%).

혼동행렬이 이유를 보여준다.

```
[구조 v3 / rag_on]   예측 positive   neutral   negative
  정답 positive             11        47          0
  정답 neutral               6        20          1
  정답 negative             24        50          0
```

정답이 negative 인 74건 중 **24건을 positive 로 예측**했다. 회피에서 벗어난 만큼
**틀린 방향으로 확신**한 것이다.

## 6.2 근본 원인 — factor 생성의 비대칭

세 버전 모두에서 `negative` 예측이 **159건 중 1~3건**이다. 구조 v3 의 유도 규칙은
`len(negative) > len(positive)` 일 때만 negative 를 내므로, 이 결과는 곧

> **모델이 악재 factor 를 호재 factor 보다 많이 생성한 경우가 159건 중 1건뿐이다.**
> (즉 158/159 에서 `positive ≥ negative`)

를 뜻한다. 정답의 47% 가 negative 인 데이터에서 그렇다.

**따라서 병목은 `impact_direction` 필드도, 프롬프트 문구도 아니다. factor 생성 자체가
호재 쪽으로 심하게 치우쳐 있다.** 방향을 어떻게 뽑아내든 그 위에서는 고칠 수 없다.

## 6.3 다음 후보

1. **호재/악재를 분리 호출** — 한 번의 호출로 둘 다 만들게 하면 모델이 균형을 맞추려는
   경향이 생긴다. "이 이벤트가 이 기업에 불리한 이유"만 묻는 호출을 따로 두면 비대칭이
   줄어드는지 확인할 수 있다.
2. **개수가 아니라 강도 가중** — 현재 유도는 단순 개수 비교다. factor 별 강도를 받아
   가중합으로 방향을 정하면 개수 동률(`neutral` 117건)이 해소된다.
3. **판별식 접근** — factor 를 먼저 만들지 말고 "이 이벤트는 이 기업에 유리한가,
   불리한가" 를 이지선다로 먼저 묻고, 그 근거를 나중에 채운다.

## 6.4 이 과정에서 잡은 자체 버그

구조 v3 의 최초 실행은 **무효였다**(fallback 318/318). `chat_json` 이
`response_model=ExternalContext` 로 응답을 검증하는데, 출력 스키마에서
`impact_direction` 을 빼자 그 검증이 반드시 실패해 전 요청이 fallback 으로 빠졌다.

단위 테스트가 이를 놓친 이유는 **`chat_json` 을 통째로 mock 해 그 내부 검증을
건너뛰었기 때문**이다. HTTP 계층만 가짜로 두고 `chat_json` 은 실제 코드가 돌게 하는
테스트를 추가해 재현했고(수정 전 `fallback_modules = ['external_context']` 로 실패),
`response_model` 을 넘기지 않고 유도값을 채운 뒤 `ExternalContext` 가 직접 검증하도록
고쳤다.

# 7. 종합 결론

| 시도 | 회피(neutral) | 정확도 | 평가 |
|---|---|---|---|
| 베이스라인 | 87% | 22.6% | 기준선(46.5%) 미달 |
| 프롬프트 강화 | 97% | 19.5% | **악화** |
| 구조 변경(방향 유도) | 74% | 19.5% | 회피는 줄었으나 정확도 개선 없음 |

1. **세 버전 모두 다수클래스 기준선(46.5%)에 크게 못 미친다.** 현재 ②단계는 방향 판정
   용도로 쓸 수 없는 수준이다.
2. **프롬프트 문구 수정으로는 해결되지 않는다** — 제약을 강화하면 회피가 늘어난다.
3. **방향 산출 구조를 바꾸면 회피는 줄지만 정확도는 오르지 않는다** — 회피가 오답으로
   바뀔 뿐이다.
4. **진짜 원인은 factor 생성의 호재 편향이다**(158/159 에서 `positive ≥ negative`).
   여기를 고치지 않으면 하류의 어떤 조정도 효과가 없다.
5. RAG 는 세 버전 모두에서 예측 분포를 유의미하게 바꾸지만(구조 v3 에서 156건 중
   32건의 예측이 달라짐), **정확도 개선은 어느 버전에서도 통계적으로 유의하지 않다**
   (McNemar p = 0.29 / 1.00 / 1.00). RAG 의 근거는 여전히 정확도가 아니라
   근거의 사실성이다(`RAG_ABLATION_RESULT.md` §2).

# 8. 상한선 측정 — 모델 문제인가, 과제가 예측 불가능한가

7절까지의 결론은 "정확도가 낮다" 였다. 그런데 **낮은 것이 파이프라인 탓인지, 과제 자체가
노이즈라서인지** 는 분리되지 않았다. "자기주식취득 공시 다음날 이 종목이 KOSPI 를 이기는가"
는 사람 전문가도 맞히기 어려운 문제일 수 있기 때문이다.

이를 가르기 위해 LLM 을 쓰지 않는 기준선과 상한선을 같은 159건에서 계산했다
(`scripts/eval_ceiling.py`).

| 기준 | 정확도 |
|---|---|
| 우리 시스템 (RAG OFF) | 17.6% |
| **우리 시스템 (RAG ON)** | **22.6%** |
| 사전확률 무작위 — *하한* | **37.9%** |
| 다수클래스 "무조건 악재" | 46.5% |
| **이론 기반 규칙** — 데이터 미참조, 18개 매핑 | **49.7%** |
| 오라클: 공시종류 룩업 — *상한(과적합)* | 55.3% |
| 오라클: 종류×종목 룩업 — *심한 과적합* | 65.4% |

**이론 기반 규칙**은 데이터를 보지 않고 재무이론만으로 미리 정한 매핑이다 — 자사주 매입·
무상증자는 호재, 자사주 처분·유상증자·감자·희석증권 발행은 악재, 구조 변경(분할·합병·
양수도)은 중립. 과적합이 아니다.

## 8.1 결론 두 가지

**(1) 과제는 예측 가능하다.** 데이터를 보지 않고 만든 18줄짜리 규칙이 49.7% 로
다수클래스(46.5%)를 넘는다. 공시 종류 안에 실제 신호가 있으며, 공시 종류만 쓰는 예측기의
상한은 약 55% 다.

**(2) 우리 시스템은 무작위보다 나쁘다.** 22.6% 는 사전확률 무작위(37.9%)에도 못 미친다.
단순히 낮은 것이 아니라 **예측 분포가 체계적으로 어긋나 있다** — 정답의 17% 만 neutral
인데 시스템은 87% 를 neutral 로 답하기 때문이다(2.1절).

정보량 관점에서 보면 격차가 더 분명하다. 우리 시스템은 RAG 로 사업보고서를 검색하고
LLM 을 9회 호출하며 5개 에이전트를 실행한다. 비교 대상인 규칙은 공시 제목만 보는
`if-else` 18줄이다. **더 많은 정보를 주고 절반 이하의 정확도를 낸다.**

## 8.2 이 측정이 앞선 기술을 정정한다

4절에서 "라벨 노이즈 때문에 정확도의 절대 수준이 낮을 수 있다" 고 적었다. 이 측정은 그
설명이 충분하지 않음을 보인다 — 같은 라벨에 대해 규칙이 49.7% 를 얻으므로, 라벨 노이즈는
22.6% 를 설명하지 못한다.

## 8.3 이 결과를 어떻게 쓸 것인가

규칙 기반 판정을 제품에 넣으면 이 벤치마크 수치는 오르지만, **실제 제품 입력은 정형
공시 제목이 아니라 자유 형식 뉴스**이므로 일반화되지 않는다. 따라서 규칙은 **비교
기준선으로만 두고 제품 경로에는 넣지 않는다.**

대신 이 문서군이 뒷받침하는 주장은 다음으로 한정한다.

- RAG 는 **기업 속성 환각을 막는다**(`RAG_ABLATION_RESULT.md` §2).
- RAG 는 **종목 특이적 근거 생성을 0/4 → 3/4 로 높인다**(같은 문서 §2.2).
- 판정 결과의 **근거 출처를 역추적할 수 있다**(`RAG_DESIGN_RATIONALE.md` §4).
- **방향 판정 정확도는 현재 사용 가능한 수준이 아니며, 그 사실을 직접 측정해 보고한다.**

## 9.3 결과

코드는 8절과 동일하고 인덱스만 교체했다. 따라서 차이는 전적으로 데이터에서 온다.

| 버전 | 조건 | 정확도 | 방향 정확도 | positive | neutral | negative | 문서 0건 |
|---|---|---|---|---|---|---|---|
| 베이스라인 | rag_on | 22.6% | 9.1% | 20 | 138 | 1 | 75 |
| v3 구조변경 | rag_on | 19.5% | 8.3% | 41 | 117 | 1 | 75 |
| **v4 새 인덱스** | **rag_on** | **27.0%** | **21.2%** | 69 | 89 | 1 | **0** |
| v4 새 인덱스 | rag_off | 20.1% | 5.3% | 14 | 144 | 1 | 159 |

- **같은 코드에서 인덱스만 바꿔 19.5% → 27.0%** (+7.5%p)
- 방향 정확도 5.3% → **21.2%** (4배)
- RAG 효과 **+6.9%p** (27.0% vs 20.1%) — 지금까지 중 가장 큼
- `neutral` 회피 144 → 89 로 감소
- `rag_off` 는 v3 와 정확히 동일한 20.1% — 인덱스를 쓰지 않는 조건이므로 비교가
  오염되지 않았음을 확인해 준다

**통계적 유의성**: McNemar 정확검정 p = 0.126 (n=156, on만 27 / off만 16). 개선 폭은
커졌으나 여전히 0.05 를 넘지 못한다.

## 9.4 남은 벽 — 악재를 여전히 예측하지 못한다

```
[v4 rag_on]   예측 positive   neutral   negative
  정답 positive        28        30          0
  정답 neutral         11        15          1
  정답 negative        30        44          0
```

정답이 호재인 58건 중 **28건(48%)** 을 맞힌다 — rag_off(7건, 12%)의 4배다. 데이터
개선이 실제로 작동했다.

그러나 정답이 악재인 74건 중 악재로 맞힌 것은 **0건**이다. 6절에서 확인한 factor 생성의
호재 편향이 데이터를 고쳐도 그대로 남아 있다.

**정리하면 이 시스템은 현재 "호재는 절반쯤 잡고 악재는 전혀 못 잡는" 상태다.** 전체
정확도가 기준선(46.5%)에 못 미치는 이유가 여기 있다.

## 9.5 시사점

세 번의 시도를 비교하면 방향이 분명하다.

| 시도 | 대상 | 결과 |
|---|---|---|
| 프롬프트 수정 | 묻는 방식 | 22.6% → 19.5% (악화) |
| 방향 산출 구조 | 답을 만드는 방식 | 19.5% (변화 없음) |
| **인덱스 데이터 교체** | **주는 자료** | **19.5% → 27.0%** |

**모델에게 묻는 방식을 바꾸는 것보다 주는 자료를 바꾸는 쪽이 효과가 컸다.** RAG 시스템의
성능이 검색 대상 문서의 구성에 크게 좌우된다는 점을 보여준다.

# 10. 평가 입력의 결함과 재측정 — RAG 효과의 조건부성

## 10.1 지금까지의 평가 입력은 공시 제목 한 줄이었다

9절까지의 모든 측정에서 모델에 준 입력은 다음이 전부였다.

```
삼성전자 공시: 주요사항보고서(자기주식취득결정)
```

금액도, 목적도, 방법도 없다. DART `list.json` 이 제목과 날짜만 주고 본문은 건당 추가
호출이 필요해, 측정을 빨리 돌리기 위해 제목만 썼다. **측정 속도를 얻고 타당성을 잃은
선택이었다.**

문제를 드러내는 사례가 있다. 삼성전자 2026-08-21 자기주식취득 공시의 정답 라벨은
`negative`(초과수익률 −5.58%p)인데, 본문을 보면 이유가 명확하다.

```
취득예정금액 : 14,999,999,992,000원 (약 15조원)
취득목적     : 임직원 주식보상
취득방법     : 유가증권시장 장내 매수
```

자기주식 취득이라도 **주주환원 목적과 임직원 보상 목적은 성격이 반대**다. 후자는 향후
유통물량 증가를 뜻한다. 이 정보는 제목에 없고 본문에만 있다. 제목만 보면 교과서적으로
호재로 읽힌다. **방향을 가르는 정보를 제거한 채 질문하고 오답으로 채점한 것이다.**

## 10.2 본문을 포함해 재측정

정답 159건, 라벨 분포, 색인, 코드는 모두 동일하게 두고 **입력만** 공시 본문(중앙값
2,652자, 157/159 수집 성공)을 포함하도록 바꿔 재측정했다.

| 버전 | 입력 | 조건 | 정확도 | 방향 정확도 | positive | neutral | negative |
|---|---|---|---|---|---|---|---|
| v4 | 제목만 | rag_on | **27.0%** | 21.2% | 69 | 89 | 1 |
| v4 | 제목만 | rag_off | 20.1% | 5.3% | 14 | 144 | 1 |
| v5 | 제목+본문 | rag_on | 20.1% | 15.9% | 67 | 90 | 2 |
| v5 | 제목+본문 | **rag_off** | **22.0%** | 18.2% | 72 | 87 | 0 |

**(1) 본문은 실제로 도움이 된다 — 검색이 없을 때.**
`rag_off` 정확도가 20.1% → 22.0%, 방향 정확도가 **5.3% → 18.2%(3.4배)** 로 올랐다.
`neutral` 회피도 144 → 87 로 줄었다. 10.1절의 지적이 맞았다.

**(2) 그러나 검색을 켜면 이점이 사라진다.**
`rag_on` 은 27.0% → 20.1% 로 내려갔고, v5 에서는 **`rag_off`(22.0%)가
`rag_on`(20.1%)을 앞선다.**

McNemar 정확검정: RAG on 만 맞음 12 / off 만 맞음 15, **p = 0.70**. 차이는 유의하지
않으며, 방향만 보면 검색을 끈 쪽이 근소하게 낫다.

## 10.3 해석 — RAG 의 효과는 입력의 정보량에 좌우된다

| 입력 | RAG 효과 | 유의성 |
|---|---|---|
| 제목만 (약 30자) | **+6.9%p** | p = 0.126 |
| 제목+본문 (약 2,650자) | **−1.9%p** | p = 0.70 |

검색이 채워주던 정보 공백을 본문이 대신 채우자 검색의 기여가 사라졌다. 즉 **RAG 는
가산적(additive)이 아니라 대체적(substitutional)으로 작동한다** — 입력이 빈약할 때
메워주고, 입력이 충실하면 더해줄 것이 없다.

본문(약 2,650자)과 검색 결과(예산 4,000자)가 함께 들어가면 프롬프트가 약 6,650자가
된다. 모델의 컨텍스트 한계 문제는 아니지만(llama3.1:8b 는 128k), 결정적 정보가 다량의
배경 자료에 희석되는 것으로 보인다.

## 10.4 이 결과가 앞선 결론을 수정한다

9절의 **"RAG 가 정확도를 +6.9%p 올린다"** 는 **제목만 주었을 때에 한정된 결과**다.
실제 제품의 입력은 뉴스 기사 본문이며 제목 한 줄보다 훨씬 정보가 많다. 따라서
**지금까지 측정한 RAG 의 정확도 기여가 실제 제품에서 재현되지 않을 수 있다.**

다만 다음 두 가지는 이 결과의 영향을 받지 않는다.

- **환각 방지** — 검색을 끄면 모델이 존재하지 않는 사업 구조를 전제하는 현상
  (`RAG_ABLATION_RESULT.md` §2). 이는 정확도와 별개의 사실성 문제다.
- **근거 귀속** — 설명이 어느 공시에 근거했는지 역추적할 수 있는 성질
  (`RAG_DESIGN_RATIONALE.md` §4).

## 10.5 변하지 않은 것 — 악재 예측 불능

다섯 번의 측정 전부에서 `negative` 예측은 **159건 중 0~3건**이다. 입력을 풍부하게 해도,
색인을 고쳐도, 판정 구조를 바꿔도 동일하다.

v5 혼동행렬에서 정답이 악재인 74건 중 악재로 맞힌 것은 `rag_on` 1건, `rag_off` 0건이다.
본문에 "임직원 주식보상" 같은 악재 단서가 있어도 마찬가지다. **이 편향은 입력이나 자료가
아니라 모델·프롬프트 수준의 성질로 확정된다.**

## 10.6 남은 과제

- 뉴스 본문 기반 평가 세트 확보(현재 NAVER 검색 API 자격증명 없음). 공시 본문은 정형
  문서라 뉴스와 성격이 다르며, 실제 제품 조건에서 RAG 효과를 다시 측정해야 한다.
- 입력이 충실할 때 검색 결과를 줄이거나(top_k 축소) 생략하는 조건부 검색 전략 검토.
- 악재 요인 생성 편향 해소 — 다섯 차례 측정에서 유일하게 개선되지 않은 항목이다.

# 11. 검색량과 입력 정보량의 관계

10절에서 본문을 포함하자 검색의 기여가 −1.9%p 로 뒤집혔다. 원인 가설은 "결정적 정보가
다량의 배경 자료에 희석된다" 였다. 이를 검증하기 위해 **입력은 그대로 두고 검색 청크
수만 5개에서 1개로 줄여** 재측정했다(`--top-k 1`).

| 입력 | 검색 청크 | RAG ON | RAG OFF | **검색 기여** |
|---|---|---|---|---|
| 제목만 (약 30자) | 5 | 27.0% | 20.1% | **+6.9%p** |
| 제목+본문 (약 2,650자) | 5 | 20.1% | 22.0% | **−1.9%p** |
| 제목+본문 (약 2,650자) | **1** | **25.8%** | 22.0% | **+3.8%p** |

`rag_off` 는 두 조건에서 22.0% 로 동일하다 — 검색을 쓰지 않는 조건이므로 `top_k` 의
영향을 받지 않으며, 비교가 오염되지 않았음을 확인해 준다.

## 11.1 결론 — 검색량은 입력 정보량에 맞춰야 한다

**희석 가설이 확인됐다.** 본문을 주는 조건에서 검색 청크를 5개에서 1개로 줄이자 정확도가
20.1% → 25.8% 로 회복됐고, 검색의 기여가 −1.9%p 에서 **+3.8%p** 로 부호가 바뀌었다.

즉 **RAG 자체가 무용한 것이 아니라 검색량이 입력 대비 과했던 것**이다. 10.3절에서
"RAG 는 대체적으로 작동한다" 고 한 해석은 다음과 같이 수정한다.

> **입력 텍스트가 이미 결정적 정보를 담고 있을 때, 과도한 검색 결과는 그 정보를 희석해
> 성능을 떨어뜨린다. 검색량을 입력 정보량에 반비례하도록 조절하면 검색은 여전히
> 기여한다.**

## 11.2 남는 한계

- **통계적 유의성은 여전히 없다** (McNemar p = 0.377, RAG on 만 맞음 19 / off 만 13).
  방향은 일관되게 양이지만 표본 159건으로는 확언할 수 없다.
- **절대 수준은 낮다.** 25.8% 는 다수클래스 기준선 46.5%, 이론 규칙 49.7% 에 여전히
  크게 못 미친다.
- **악재 예측 불능은 그대로다.** 여섯 번의 측정 전부에서 `negative` 예측이 0~3건이다.
  검색량 조절로도 바뀌지 않는다.

## 11.3 제품에 대한 함의

현재 `document_retrieval._TOP_K` 는 5 로 고정되어 있고 입력 길이와 무관하다. 실제
서비스 입력은 뉴스 본문이므로 이 실험의 "본문 포함" 조건에 가깝다. 따라서 **입력 길이에
따라 검색량을 조절하는 것이 우선 개선 과제**다. 다만 본 실험은 공시 본문 기준이므로,
뉴스 본문에서도 같은 관계가 성립하는지는 뉴스 기반 평가 세트로 확인해야 한다.
